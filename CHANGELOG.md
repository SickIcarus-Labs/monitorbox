# Changelog

What changed in each version of the MonitorBox app, in plain words. Every change that reaches a user adds a line under **Not on stable yet**. When a version is promoted to the stable channel, that heading is renamed to the version and a new empty one is started.

Authors mark a few entries as highlights by putting [highlight: one short sentence.] right after the ticket number. A box catching up on more than ten versions at once is shown only those short sentences first, with "Show everything" for the rest; the tag is not shown anywhere else.

Versions move through three channels: **dev** (newest, may be rough), **beta**, then **stable**. A version listed here may not have reached your channel yet; Settings, Updates shows which one you follow.

## Not on stable yet

- **1.9.22** More security fixes for boxes opened to the internet. Before you sign in, MonitorBox now reads only small requests and closes connections that go quiet for a minute, so a stranger cannot tie up the Pi. Failed passkey tries only slow down the address they came from, so nobody can keep you from signing in with your passkey. A visit your proxy passes on always counts as an outside visit, even when the proxy's forwarded address cannot be read, and the first password can never be set through a proxy. If something is passing visits on like a proxy but is not listed under Settings, Sign-in and security, the log says so. Icons are served only by their own names.
- **1.9.21** [highlight: Security fixes for boxes opened to the internet.] Names that come from devices and other systems (container labels, camera ids, machine names, a managed site's name) are now always treated as plain text by the buttons that use them, so a crafted name can never run in your signed-in browser. A site tab now only passes on the kinds of answer a MonitorBox gives (data, images, logs, backups), never a web page of its own.
## 1.9.19 to 1.9.20 (stable, October 31)

- **1.9.20** (#331) [highlight: Port errors now say how many were seen and when, not a scaled-up hourly rate.] Port errors and packet drops now give the real count and the window: "errors rising (133 in the last 15 min: 133 receive, 0 transmit, about 1 in 56,000 packets)" instead of "about 532 an hour", which read like a fault lasting the whole hour when it was a short burst. The share of packets reads as "about 1 in N packets". The same wording is used on the front page, the Port errors page, a switch's or server's detail (including the other end of the link) and in alerts. What raises the alert has not changed.
- **1.9.20** The log no longer says a module "stopped unexpectedly" when MonitorBox restarts for an update. A graph or check still finishing found the module MonitorBox had just stopped and started it again; nothing is started once MonitorBox is shutting down.
- **1.9.19** (#334) Each module now starts once when MonitorBox restarts. The LAN sampler or the graphs could ask for UniFi Network or SNMP a moment before the start-up batch launched it, start their own copy, and then the batch started it again and stopped the first, so its checks went Unknown for a few seconds at every restart. They now wait for the batch, and the batch leaves a module alone that is already running.

## 1.9.17 to 1.9.18 (stable, October 31)

- **1.9.18** The move of DNS into the Internet card (1.9.17) now also moves DNS servers that check something else too, such as their Pi-hole admin page (Turnberry's did, so they stayed in their own card). The log now says when DNS items were moved, or why they could not be.
- **1.9.17** DNS servers now sit in the **Internet** card instead of a card of their own. New boxes set them up there, and a box set up earlier moves them there once by itself (the DNS servers and the DNS group only; anything else you filed under DNS stays put).
## 1.9.15 to 1.9.16 (stable, October 31)

- **1.9.16** (#336) [highlight: Fixed Settings and other pages sometimes failing to load through a proxy.] MonitorBox's web server could only hold 5 new connections waiting at once (the standard default). When a page asked for eight or nine things together while the Pi was busy, the extra connections were refused: through Caddy that showed as "502", and on its own as a page stuck loading. It now holds 128. On the owner's Pi the kernel had counted 14,697 refused connections.
- **1.9.15** (#336) Settings no longer sits on "Loading settings…" for good. When a read gets no answer it is asked again; if that fails too, the page now says which request failed and how ("versions: no answer in 12 s") with a **Try again** button, and the same line goes into the log under "browser". The box never sees a request that is stuck in the browser, so this is how the cause gets on record.

## 1.9.14 (stable, October 31)

- **1.9.14** (with UniFi Network 0.2.27) Three fixes for short blips overnight. Web checks now wait up to 10 seconds for a page (was 5), so a service on a busy server, such as Radarr on Goliath during the nightly backup, is not marked Degraded. The UniFi flow log is read on its own lane, so status checks never wait behind it (UniFi Aggregation went Unknown for a minute at 3:32). And a port's history is kept when an error or drop count goes down a little (924 to 923); only a fall to less than half, as a restart does, starts the port again.
## 1.9.13 (stable, October 30)

- **1.9.13** (with SNMP 0.3.13) A NAS disk that is too warm now says why it is Degraded: "status Good, 57 °C (hot, limit 55 °C)". SSDs get a higher built-in limit, 70 °C instead of 55 °C, and say "SSD" on their line. Each disk can have its own limit: open the system, Edit monitoring, Disk temperature limits (empty uses the built-in one), the same as a UniFi Protect drive.

## 1.9.7 to 1.9.12 (stable, October 30)

- **1.9.12** Errors and packet drops that stay below the alert line are now shown instead of hidden. The Port errors page has a **Below the alert line** list, and the network map adds a grey line to the port, for example "780 errors an hour (0.00015% of packets), below the alert line". Nothing about alerting changes.
- **1.9.11** Fixed a port starting over at "learning" when its error count dipped for a moment. UniFi sometimes reports a port's errors a little lower than before (402, then 325) while the port is busy; the port watch read that as the device restarting and threw away the port's history, three times in one evening on the WAN port. When the packet counts keep going up, the old figure is now held until the counter passes it, so nothing is lost and no errors are invented. A real restart, where the packet counts start over too, still starts the port again.
- **1.9.10** Port errors now count from 0.01% of the packets (1 in 10,000), down from 0.1%. That is about where a single download starts to slow, so a cable or module that is starting to fail is reported sooner, while a busy link with a few hundred errors an hour stays quiet. Packet drops stay at 0.1%.
- **1.9.9** Things that cannot be checked because the same source is not answering (a UniFi console, a Portainer server) now show as one entry under Needs attention, such as "UniFi Network", listing what it affects, instead of one entry each. Check now on it checks all of them. Each item still keeps its own Unknown state, and the headline still counts every item.
- **1.9.8** Port errors are now judged against the traffic, the same as packet drops. Where the device reports packet counts, errors raise the Port errors item only when they are at least 0.1% of the packets in the same 15 minutes, and the line says the share. A few hundred errors an hour on a link moving a big download no longer raise it. Devices without packet counts keep the old rule.
- **1.9.7** (with UniFi Network 0.2.26 and UniFi Protect 0.1.7) A busy UniFi console no longer turns every UniFi item and camera Unknown at once. The UniFi modules now wait up to 15 seconds for an answer (was 8), and something that was healthy and then cannot be checked waits out the same grace as a failure (2 in a row over 60 seconds by default) before it shows Unknown; until then it stays healthy with a heads-up line. With the grace set to 1 and 0, Unknown still shows at once.

## 1.9.0 to 1.9.6 (stable, October 30)

- **1.9.6** (#336) For finding why Settings sometimes will not load: the performance report now lists requests that are still waiting (a request that never finishes used to be missing from it), and the debug log notes any request that took over a second.
- **1.9.5** (#334) The log's "started" line for a module now says which process it is, which process it stopped and who asked for the start. At every restart UniFi Network is started twice a second apart and its checks flip to Unknown for a few seconds in between; this shows where the second start comes from.
- **1.9.4** (#333) Modules now have their own change notes. Settings, Versions shows **What changed** under a module update, the same as for MonitorBox itself. Each module has a short note on what it does to start with, and every later version adds a line.
- **1.9.3** (#329) The debug log now names the device on every module call ("call snmp.counters for Goliath took 57 ms"), so a slow call can be tied to the device that was slow. Only the device's name is logged, never its address or login.
- **1.9.2** (#329) The Logs page's first filter no longer offers two choices that mean the same. While debug logging is on, "All" already includes debug lines, so the other choice is now "All except debug" (the old "All, with older debug lines" shows only while debug is off).
- **1.9.1** (#315) The log now records the raw numbers whenever a port's packet-drops counter falls by itself (what it read before, what it reads now, and what MonitorBox carried on from). This was missing, so a strange drops figure could not be traced.
- **1.9.0** (with SNMP 0.3.12, UniFi Network 0.2.25, #315) Packet drops no longer raise the Port errors item when they are noise. A server's network card (Arrrrr3's eno3 discards about 650 frames a second the system has no use for) no longer counts its receive drops: a card that really loses frames shows receive errors, which are still counted, and its transmit drops still count. Everywhere else, drops count only when they are at least 0.1% of the packets in the same 15 minutes, when the device reports packet counts (SNMP and UniFi now read them); the line says the share. A device with no packet counts keeps the old rule. The port history now also keeps packet counts (a few more bytes per reading).

## 1.7.22 to 1.8.4 (stable, October 30)

- **1.8.4** (#329) The log now names a port the way you know it ("Bonus Room, Port 7") when the port watch starts, resets, forgets or drops its readings, instead of an internal key with the end of a hardware address.
- **1.8.3** (#329) The Logs page's first filter, "All", now includes debug lines whenever debug logging is on (it used to hide them until you chose "Include debug"). With debug off it is the normal log, as before. The last choice reads "All, with older debug lines" for debug lines written earlier.
- **1.8.2** (with SNMP 0.3.11, #330) Fixed a device with many checks flipping most of them to Unknown every round. On Goliath (about 40 checks) the SNMP module let only four calls run at once and turned the rest away at once as "that device is still busy", so about 20 checks went Unknown together and came back 15 seconds later, again and again (the new Logs page made it plain). Each device now has its own four workers and checks wait their turn; a call is turned away as busy only after waiting 10 seconds. A device that really stops answering still cannot hold up the others. The four-at-a-time limit came from #327.
- **1.8.1** (#329) Fixes on the Logs page from the first real use. Tapping a line now visibly opens it (a highlighted row with the full date and time, level, source and entry number, and an "Only <source>" button); before, a line only grew when its text was long, so a short line looked like nothing happened. A filter you had just picked kept the page waiting behind the "new entries" button; it no longer does. New lines now wait only while a line is open, the search box is being typed in, or text in the list is selected. The first filter reads "All (no debug)" to say that debug lines need "Include debug".
- **1.8.0** (#329) [highlight: MonitorBox now keeps a log you can read: Settings, Advanced, Logs.] A log of what MonitorBox itself did and saw. Settings, Advanced has a Logs row ("All quiet" or "N errors in the last day") that opens its own page: newest first, grouped by day, tap a line to open it, filter by level, source or search. New lines arrive at the top while you watch and never move the page once you scroll (a "N new entries" button appears instead). The menu has Download logs, Copy last 100 lines and a Debug switch that turns itself off after 24 hours. The normal log keeps 5 files of 1 MB for 14 days; debug keeps 5 files of 10 MB for 3 days, so neither can fill the SD card, and one noisy source is cut off for the minute and says so. Checks changing state, alerts sent, not delivered or given up, modules starting, stopping or timing out, backups, updates, sign-ins and pairing are all written. Passwords, tokens and web-address paths are never written. When MonitorBox itself fails (a module that will not start or keeps timing out, an alert that could not be delivered after every try, a backup that fails) the bell says so with a Logs link. The weekly full backup carries the normal log, never the debug log. This replaces the 1.7.26 `port-trace.log`: the port watch now writes its start, reset and forget lines to the log, and a one-line-per-round summary to debug.
- **1.7.27** (#328) Fixed ports that sat at "0 min of readings" and never finished learning. The port watch checks every 10 seconds but keeps one reading a minute, and it stored the newest reading with the time of the latest round, so a minute never seemed to have passed. A port whose history had started over stayed at a single reading until a round happened to run slow. It now keeps one reading each minute properly (the readings kept for a day are about 1,400 per port, up from a handful). Nothing else changes.
- **1.7.26** (#328) A diagnostic for a port that never finishes learning. MonitorBox now writes one line to `port-trace.log` (next to the port history) each time a port's history is started, thrown away or forgotten, with the counters at that moment. Names and numbers only; the file is cut back past 200 KB. Nothing else changes.
- **1.7.25** (#328) A port whose packet-drops counter shrinks on its own (some network-card drivers do this, for example Arrrrr3's eno3) no longer starts over. Only the drops carry on from where they were; the errors and link-flap history stay, and the port keeps its learning. The page still counts the occurrence. If errors or link flaps also fall, that is still treated as a restart and the history starts again.
- **1.7.24** (with UniFi Network 0.2.24, UniFi Protect 0.1.6, #328) When the UniFi console stops answering, every UniFi and Protect check now says so at once ("cannot reach the UniFi controller ... timed out") instead of each one waiting out its own timeout behind the one before and reading "the module did not answer". On Oct 29 a console that went quiet for about six minutes turned a hundred checks Unknown with that confusing message. They are still Unknown, never Failed; the wording and the recovery time are what change (one real try every 10 seconds).
- **1.7.23** (with NUT 0.1.4, UniFi Protect 0.1.5, Wake on LAN 0.1.2, #328) More small fixes from the documentation pass. A NUT server that accepts the connection but never answers now says it did not answer in time, instead of "cannot reach". A UniFi Protect login that is accepted but returns no session now waits a minute before trying again, like any other failed login. Adding Protect from your UniFi Network login no longer copies the Network console's port. Wake on LAN now refuses an IPv6 broadcast address (the packet goes out over IPv4) and its "no wake settings" message names the real screen. The install guide and the Port errors page no longer say things the code has moved past.
- **1.7.22** (with SNMP 0.3.10, Scrypted 0.2.3, Portainer 0.1.7, NUT 0.1.3, UniFi Network 0.2.23, UniFi Protect 0.1.4, #328) Small fixes found while writing the documentation. A VPN tunnel you paused on purpose in UniFi now shows as Degraded with the word "paused", not as Down. A UPS that reports both "on battery" and "low battery" is announced as the low battery. A garbled message can no longer stop the SNMP module. Portainer no longer follows a redirect with your access token; it tells you the address redirected. A Scrypted connection that asks for the certificate check is now really checked, even when another Scrypted connection does not ask. Error messages that said "Use Re-detect" now name the real button, "Pick what to watch".
## 1.7.10 to 1.7.21 (stable, October 29)

- **1.7.21** (#324) The other site's tab now shows its "(managed by)" line expanded the first time it is opened. Before, it appeared only after tapping away and back, because the page asked the other site for its pairings at the next 10-second round.
- **1.7.20** (#327) The brief "SNMP: that device is still busy" Unknown that appeared on a switch or the NAS since 1.7.12 is gone. A slow switch normally has a report, a counter read and a check going at once, and the limit of two let the check be turned away. The limit is now four, which still stops a device that has really hung from using every worker.
- **1.7.19** (#324) The other site's tab now really shows its "(managed by)" line expanded. In 1.7.17 and 1.7.18 the page asked the other site for its pairings through the Sites screen's address, which a managed site refuses to pass on (on purpose: a main box must not manage another box's pairings), so the line stayed plain. It now uses a read-only view that holds only names, addresses and link state.
- **1.7.18** (#324) Wording on the other site's tab: the line reads "Broad Leaf (managed by)" and its rows are the same as on the main site: Internet address, Connects to, Gateway.
- **1.7.17** (#324) The other site's tab now shows its side of the pairing the same way. Opening Turnberry's tab, "Managed by Broad Leaf" is an expandable line with Broad Leaf's internet address, the address its calls come from, and its gateway, each with a live light. Before, only the main site showed those lines.
- **1.7.16** (#324) A paired site that is down now appears under "Needs attention" on the main screen, the same way a server in trouble does, with the reason and a Check now button. The headline ("Everything is fine") and the attention count still describe this site only. A site link is checked every 10 seconds and confirmed in 20 (was every 15 and 30), so its tab goes red sooner after a VPN or site outage.
- **1.7.15** (with SNMP 0.3.8, #327) One SNMP device that stops answering no longer makes other devices go Unknown. On Oct 29 a call to Goliath hung for 40 seconds and Aggregation and Switch 2 showed "snmp did not answer check" at the same moment: the SNMP module has 8 workers and a few hung calls to one device could take them all. Now at most 2 calls per device run at once; a third is answered straight away (Unknown, "that device is still busy with earlier requests") instead of waiting for a worker.
- **1.7.14** (#324) Remote-site alerting, tightened after the first real test. A paired site's link is now confirmed in 30 seconds instead of 60, and a link whose last good answer is more than 35 seconds old no longer keeps saying "answering". The lines under a site on the main screen now have live lights: the internet address and the gateway each light by whether they answer a ping from here, and "Connects to" by the link. An internet address is only trusted to prove a site down once it has answered a ping from here at least once (some firewalls never answer ping from outside), otherwise a silent link stays Unknown.
- **1.7.13** (#324) The expanded remote-site line on the main screen no longer has a "Details" row: the top of the card already opens the same side view.
- **1.7.12** (#324) A remote site that loses its internet now shows as down. The two sites tell each other their public (internet) addresses over the link, which they already poll every 10 seconds, and when the link goes silent each one judges it by pinging the other's public address from outside the tunnel. If the address still answers, the link shows Degraded ("its internet is up, the link or MonitorBox there may be down"). If it doesn't and this box's own internet is fine, it shows Down. If this box's own internet is down too, it stays Unknown, because it can't tell whose line it was. The address comes from the UniFi gateway when there is one; a gateway that reports a private address (double NAT, or a UniFi glitch) is treated as "can't tell": nothing is shared and nothing is guessed, and it is read again every minute. Without a UniFi gateway, one request to a public address page (Cloudflare's trace page) is made, at most every half hour. The address is shown in Settings, Sites, and in the check text. Sites on an older version simply show their address as "not shared yet" and keep the old Unknown behaviour. The sites also tell each other their gateway address; once a gateway has answered a ping from the other side while the link worked, a silent link whose internet is still up says which part failed: the gateway is silent too ("the VPN between the sites is down", shown red) or it answers ("MonitorBox on that site may be down"). A gateway that never answered is ignored, and so is one whose address is the same on both sites. Both sites need this version.
- **1.7.11** (#325) A real outage now shows in the history bars even when most of that hour was healthy. Before, a stretch of Unknown ranked below Healthy, so a 2-minute loss of a site link (or a 45-minute one that straddled two hours) left the bar solid green. Now an Unknown that lasted longer than the check's confirmation time (by default 2 checks / 60 seconds) shows as blue, and a shorter one is still treated as a blip, the same way a short Down is. A known Down or Degraded in the same hour still shows instead of Unknown. The "Could not be checked" list follows the same rule.
- **1.7.10** (#322) A restart no longer makes a port start its learning again. The app now saves the port history as it stops (an update, a restart, or a container stop) instead of relying on a save that could be up to five minutes old. A network card with a 16-bit drops counter, such as Arrrrr3's eno3, goes round every 10 to 15 minutes; if that happened between the last save and the restart, the box could not tell a lap from a reset and began that port's 30 minutes of learning again.

## 1.4.3 to 1.7.9 (stable, October 29)

- **1.7.9** (with SNMP 0.3.7, #321) Reading a big switch is much faster. Aggregation lists 486 interfaces but only about 26 are real ports; the rest are empty stack slots, port-channels nobody watches and tunnels, and every full read (the first counters reading, the network map, Re-detect) was asking for all of them. Now a device with more than 64 interfaces is checked first, and interfaces the device itself says are not present, or are tunnels, loopbacks or VLANs, are skipped. Down ports and link aggregations are never skipped, a device that doesn't say is read in full, and Re-detect and the network map note how many were left out.
- **1.7.8** (#100, #102) A settings backup now holds settings only: the history is no longer in it, only in a full backup. Restoring a settings backup keeps the history your box already has (and Undo gives back everything as it was). Full backups copy and check each file in one pass instead of two, and the last backup's step timings now show in the performance report. **This one needs the container image re-pulled** (new image 1.0.3); the bell and Updates page will say so.
- **1.7.7** While a backup is being made, the Backups page shows a moving bar and a line saying so ("Making the backup… This takes a few seconds.", or for a full backup "…can take about half a minute."), and the backup buttons are switched off until it finishes. Before, the buttons looked dead for the whole wait.
- **1.7.6** Making a backup is fast again. A settings backup of 51 KB took about 17 seconds on a Raspberry Pi, because making any backup also scanned every older backup from start to end to decide which to delete, and full backups are large. Each old backup is now read once (just its label) and remembered.
- **1.7.5** (#98) A module is installed only when it is needed. A new box starts with Wake-on-LAN only (nothing can detect that you want it); a module such as UniFi, Portainer, Scrypted, SNMP or UPS (NUT) installs itself the first time you add or test a device of its kind, and a restored backup fetches the modules its connections use. The bell, the Update counts, Update all and automatic updating cover only modules you already have, so Hello on dev (or a module for equipment you do not own) no longer shows up as "ready to install". Boxes that already have modules keep them, and installing by hand from the Updates page still works.
- **1.7.4** Making a backup now shows up in the list as soon as it is done. Before, a slow backup (a full one) could leave the old list on screen until you refreshed the page.
- **1.7.3** The Hello sample module is for the dev channel only. A box on beta or stable now removes it by itself (at start and when you change channel). It does not come back by itself; on dev you can install it by hand.
- **1.7.2** An installed module that is idle (not running yet, such as Hello) now has an Uninstall button on the Updates page. Before, the button only appeared while a module was running, so an idle one could not be removed.
- **1.7.1** (#317) Temperatures and drives are tidier and adjustable. On a card, three or more UniFi temperature checks fold into one line ("UniFi temperatures · 3 temperatures · all good") that opens on tap, and by itself when one is hot, the same as the cameras and VPN tunnels. Protect drives fold the same way once there are three. Each device's or drive's warning limit can now be changed: open it, tap Edit monitoring, and set "Warn when hotter than (°C)". Empty uses the built-in limit (80 °C for a switch or gateway, 55 °C for a drive).
- **1.7.0** (#310) Three fixes to the main screen. The card history bars no longer go missing: the box built each card's 24 hour bar slowly (about two seconds on a Raspberry Pi when it was busy), so a request could fail and leave a card bare until the next minute or a refresh. It is now built many times faster, a bar that could not be fetched is asked for again within a few seconds, and a bar already on screen is never lost to a failed request. On the Updates page, "Update all sites" now appears as soon as "Check all sites" finds an update at a site, and goes away again when it is installed, without switching tabs.
- **1.6.44** (#310) The bell now looks for news every 15 seconds (it was every minute), and straight away when you come back to the page. It asks nothing while the page is not in front. A site that is slow to answer is never asked twice at once. An update on another site used to take up to a minute, after its restart, to reach the bell; now a few seconds.
- **1.6.43** (#320) A big update jump now shows a short version of "What changed" first. When a box is catching up on more than ten versions at once (a box on the stable channel, say), "What changed" opens with "Highlights from N versions": one short sentence for each of the changes we marked as the important ones, newest first, with "Show everything" underneath for the full list. A normal one-or-two-version update looks as before.
- **1.6.42** [highlight: New drive temperature and health checks for UniFi Protect.] (#317, with UniFi Protect 0.1.3) New "Drives" checks for the recording drives in a UniFi Protect recorder. Re-detect offers one per drive; it shows the temperature ("45 °C") and reads Degraded at 55 °C or above (editable per drive), or when its bad-sector count grows, its health or state other than good/normal, or any fault reason. Bad sectors only warn when the count grows while the box is watching (a drive that has always had a few stays quiet). It uses the monitor's "must last a while" setting, so a brief spike stays quiet. A drive model Ubiquiti does not list ("hddNotCompatible") is ignored, as Protect's own screen does. A console that does not answer reads Unknown, never Failed. This reads one more page from the recorder (its own status, read-only).
- **1.6.41** [highlight: New temperature checks for UniFi devices.] (#317, with UniFi Network 0.2.22) New "Temperatures" checks for UniFi devices. Re-detect offers one per device that reports a temperature; it shows the hottest reading and the fan speed ("54 °C · fan 31%"), and reads Degraded when the device is at or above its limit (80 °C unless you change it) or says it is overheating. It uses the monitor's "must last a while" setting, so a brief spike stays quiet. A device with no sensor is not offered, and a controller that does not answer reads Unknown, never Failed.
- **1.6.40** (#312) "What changed" now copes with a big jump, such as a box on the stable channel catching up many versions at once. It lists every version that has notes (up to 200), newest first, and leaves out versions released before notes travelled with releases.
- **1.6.39** (#314) Tidier Updates page. The buttons now sit together in one row at the top: "Check now", "Check all sites" (only when a site is linked; it checks this box and every linked site and names any that did not answer), "Update" (only when this box has an update waiting; it used to be "Update all (N)", and the updates listed below can still be installed one at a time) and "Update all sites" (only when a linked site has an update waiting). The line of text beside the old Update button is gone.
- **1.6.38** (#314) "Update all sites" now reloads the page when this box updates itself. Before, the page said "This box is restarting" and stayed there until you refreshed by hand; now it shows "Restarting…" and comes back on its own, like any other app update.
- **1.6.37** (#314) The "Update all sites" button now shows only when an update is waiting at this box or at a linked site. It used to show whenever a site was linked.
- **1.6.36** (#311) History now names every port in a long Port errors stretch. A stretch used to keep only the ports named when it began, so a port that started rising later in the same stretch (like Guest Room, Port 8 at Broad Leaf) was never mentioned. Ports that join are now added to the reason, for example "...; also Guest Room, Port 8", up to the same length limit.
- **1.6.35** (#312) [highlight: The Updates page has a "What changed" link.] The Updates page now has a "What changed" link on the MonitorBox app: when an update is waiting it lists what changed in every version between yours and the one on offer (newest first, in plain words); when you are up to date it shows what your version brought. The notes travel inside the release itself, so MonitorBox does not need to reach any other site. Versions released before this one carry no notes. Modules have no changelog yet, so only the app has the link.
